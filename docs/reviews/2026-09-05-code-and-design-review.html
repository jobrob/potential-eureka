The strongest reason to change the roadmap is a set of concrete observation defects. Some strategically different states are indistinguishable to the current policy. More compute or a more elaborate encoder cannot recover information its inputs omit.

Keep the existing native engine and simple PPO baseline. Defer CUDA, the original worker-loop rewrite, large training runs, and speculative model changes.

This review assesses code, assumptions, experiment design, and outstanding work. It does not treat “implemented,” “exact,” or “gate passed” as proof of every intended property. Confirmed findings

P1 means address before relying on the affected learning or evidence claim. P2 means a bounded correctness or reliability repair. These are current-tree findings, not claims about which commit introduced them.

1 · P1 · Observation information loss

Track-relative normalization erases absolute corner limits.

Each speed limit is divided by the largest limit on that track, and that divisor is not supplied to the policy. A track whose corners all limit speed to 1 therefore looks identical to the same geometry with every limit set to 2. These cases have different heat costs.

Reproduced: two generator-produced tracks, six corners each, identical seeded player state: the complete 104-value observations and legal GEAR masks match. The native observations also match. Crossing a corner at speed 3 costs 2 heat in one case and 1 in the other.

Change: preserve absolute units using fixed scaling, or supply the per-track scale explicitly. Audit track length, corner length and lane information by the same principle. Start with a small flat representation; no attention model is required to fix this.

features.py:203–215. The probe proves information loss, not its frequency or contribution to the measured win rate. The limit combinations are possible under the default generator, though the probe forces them for a deterministic reproduction.

Status: Implemented as codec v4. Corner limit, length, and lanes use fixed scales (5, 90, and 3). Codec v3 still divides by that track's own maxima, so a historical checkpoint keeps its old inputs on the Python encoder. The native collector is codec v4 only and refuses a codec 3 policy instead of scoring it on the new inputs. The native schema hash is d3-a5-v4-r104-a516-p6-r200-c424-t90.

2 · P1 · Missing public decision context

REACT cannot reliably distinguish a dangerous revealed move from a safe one.

The observation includes current position and legal reaction flags, but omits revealed speed and the turn's movement origin. The engine uses those omitted fields to calculate which corners were crossed and the heat bill. After movement, the forward-looking corner slots alone do not describe that bill.

Reproduced: controlled transient states with the same observation and mask, speeds 5 and 1, and different turn origins. With no extra movement, the engine's corner check spins out the first car and leaves the second safe.

Change: encode current effective speed and sufficient movement/corner-cost context at REACT and SLIPSTREAM. Test strategically different states that require different decisions, as well as hidden-information leakage.

features.py:387–430; phases.py:553–599. This is a controlled state-pair reproduction, not two replayed complete race histories. No strength impact was measured.

Status: Implemented in codec v4. Phase indices 10–16 carry revealed corner speed, turn origin, heat at that speed, heat at one speed faster, heat two spaces further along, and track length. They are written from the player and the track for every decision, including no decision. Indices 17–18 stay 0. Codec v3 leaves 10–18 at 0.

3 · P2 active feature / P1 before reward reuse

The finish-distance convention is wrong, and the deferred margin has a deeper problem than the design admits.

Racing starts at lap 1, but remaining distance uses lap × length + position as completed distance. At position 0 on the final lap of an 83-space track, the feature already says zero distance remains. One lap remains. Other inputs can partly compensate, so this alone does not establish a training ceiling.

The margin proposal is more seriously flawed: the game ends when all players finish; terminal_margin assigns every finished player zero remaining distance. Consequently the margin is zero at every normally completed race, regardless of lap count. The collector adds it at game end. Moving the experiment to a multi-lap bed alone will not fix this.

Change: use a tested race-progress definition with one-based lap semantics. Redesign a future target around an informative event or recorded finish timing, and prove nonzero, useful labels on actual completed traces before training. An extra terminal reward is also not automatically a dense intermediate learning signal.

features.py:294–299; spaces.py:248–263; game_state.py:101–104; multiseat.py:592–611; A6 design, status and follow-up. Margin coefficient is currently zero, so the inactive target is not corrupting the adopted reward.

Status: The observation and the unused margin label are corrected. Laps remaining count the current lap. Distance to the finish uses completed distance (max(lap, 1) - 1) * length + position. When every car has a finish order, the margin uses that order. margin_coef stays 0, so the training reward is unchanged. The corrected margin has not been trained.

4 · P1 for the proposed collapse guard

The logged entropy is not the entropy driving the controller.

The trainer stores pre-update rollout entropy as record["entropy"], then expands **losses, which contains another entropy. The latter overwrites the former with an average measured during optimization. The controller itself receives the intended pre-update value; the record and proposed guard can disagree with it.

Reproduced: injecting an optimizer diagnostic of 9.876 produced recorded entropy 9.876 while the controller's minimum recorded input was 1.24593.

Change: distinct rollout_entropy and update_entropy fields, plus an explicit guard definition. Add per-phase entropy and legal-action count as diagnostics: a changing mixture of two-choice and many-choice decisions changes aggregate entropy even without a collapse.

phase1.py:482–487; ppo.py:275–279. Existing historical entropy columns must be interpreted according to this actual implementation.

Status: Implemented. New trainer rows store rollout_entropy and update_entropy, plus per-phase entropy, legal-action count, and row count. Approximate KL, clip fraction, and explained variance are logged and do not stop an update. There is no entropy key for the loss dict to overwrite. Older rows that contain entropy still hold the optimizer value.

5 · P1 for track/starting-seat interpretation

Globally balanced races can still confound track and starting seat.

The harness uses g % seat_count for the focal seat and g % track_count for the track. With 40 tracks, a particular track always gets the same focal seat at two and four players; at six players it sees only one parity of seats. The proposed design's global balance rules permit this.

Reproduced: track 0 in a 200-race cell gets seat 0 on all five races at two and four players, and only seats 0/2/4 at six players.

Change: build coordinates explicitly and rotate starts within each track across repetitions. Exact all-six-seat coverage is impossible with five repeats, so balance coverage as far as the budget permits and document the omission. Preserve these coordinates across contenders. Current comparisons remain comparisons on their sampled coordinates; this finding particularly limits broader starting-seat and geometry claims.

eval_harness.py:327–328; 32K balance contract.

Status: Implemented. Race g uses track g % track_count. The focal seat is (track_index + repeat_index) % seat_count. Five repeats still cannot cover six seats. The race seed is still base_seed + g.

6 · P2 · Recovery reliability

Checkpoint and receipt are individually atomic, but a failed save can destroy the last resumable pair.

The writer replaces the checkpoint first, then replaces its checksum sidecar. A crash between those operations leaves the new file with the old receipt. Verification correctly refuses it, but the old verified checkpoint has already been overwritten.

Reproduced: an injected failure during sidecar publication left only an invalid pair; the previous checkpoint was no longer retained. This is safe rejection of unverified data, but not the promised bounded recovery gap.

Change: write immutable numbered checkpoint/receipt pairs and publish a small latest pointer only after both are complete; retain at least one previous verified pair. Add a failure-injection check. Existing clean fresh-process continuation tests are valuable, but test a different property.

Status: Implemented. A save writes <name>.generations/000001.pt and its receipt, then replaces <name>.latest only after those bytes match. The previous published pair is kept. A failed receipt write leaves the prior pointer loadable, and an old path-plus-sidecar file still loads until a pointer exists.

training_state.py. The original failure was injected only into disposable temporary files.

Where I would change the designs

Design judgment · revise before implementation

The 32K comparison is useful, but its meaning and stopping rule need tightening.

I agree with three fresh seeds, frozen selected checkpoints, identical evaluation coordinates, and separate operational and learning evidence. An unchanged historical baseline is adequate for a practical adoption decision; a new small-rollout control is only necessary if the question becomes causal attribution.

  • Use an actual-transition stopping rule. Thirty requested 32,768-row updates total 983,040 rows. Draining games often supplies the difference, but does not contractually guarantee it. In the existing soak, 1M was crossed at update 27 and update 30 reached 1,114,422. Define first-crossing selection and explicit hard iteration/time caps; do not make success depend on incidental overshoot.
  • Call out the changed training dynamics. The current trainer picks one seat count and one opponent configuration for an entire update. Thirty updates give only six updates per seat count, versus 976 nominal updates in the registered 1,024-row G0002 recipe. Snapshot spacing, opponent residence time, controller response and within-batch diversity change too. Equal sample exposures do not make these learning schedules equivalent.
  • Measure update size before choosing a PPO repair. Log approximate KL (how far the new action distribution moves), clipping fraction and value explained variance. Present code logs loss terms but not these diagnostics. Clipping alone does not guarantee a small policy change; OpenAI's PPO documentation explicitly discusses this. Add measurement first; KL-based early stopping would itself change the recipe.
  • Treat three seeds as a pilot adoption decision. The point gates are an engineering tolerance, not a precise non-inferiority confidence claim. Keep the full run × ruler × seat matrix visible. For track-population uncertainty, resample tracks as blocks while retaining all paired contender results, and distinguish that uncertainty from training-seed uncertainty.
  • Prioritize the decisive evaluation. Promotion provides the actual same-band decision; 10,800 additional milestone races are diagnostic. I would make promotion first and consider a smaller predeclared milestone screen, saving budget for replayable error examples. Calibrate evaluation throughput with the actual V2 rulers before treating the 75–80 minute estimate as established.

Status: Revised in the 32K design on 1 October 2026. The campaign is not authorized and its scripts do not exist.

Design judgment · change the next-work order

Input correctness deserves priority over architecture, scale and an exhaustive investigation queue.

The parent plan's statement that PPO handles partial observability “for free” is too strong. PPO can learn from incomplete observations, but the feed-forward policy cannot distinguish identical inputs. It does not acquire memory of a revealed speed that the encoder omits. Fix accessible public information before considering recurrence or opponent inference. Recurrent PPO adds explicit recurrent state; it is not a property of this existing MLP.

I would also narrow conclusions from old gates. A3 tested one static-feature action head on Tiny-Heat, not every action-scoring architecture. A4's small-seed result supports retaining the cheap default, not ruling out structure forever. A6 never tested a useful completed-race margin. Respect the recorded decisions, but do not elevate those experiments into universal exclusions.

Before another action-head experiment, audit which legal choices the codec can express. DISCARD deliberately exposes only “discard the lowest k cards.” A stronger scorer cannot choose a discard set that the representation excludes. This is an intentional restriction to evaluate, not a newly proven rules bug.

My preferred next sequence: fix entropy, coordinate generation and recovery; specify and test observation sufficiency using small counterexamples; then choose the campaign's question explicitly. If the immediate aim remains assessing adoption of the existing runtime/recipe package, run the amended 32K pilot with the legacy observation and make no broader strength claim. If the aim is the fastest route to stronger play, my preference is a newly declared native recipe with corrected inputs, compared against the preserved G0002 baseline. That comparison changes inputs and runtime together and must be described accordingly.

Do not silently amend the supposedly frozen recipe. G0005 is still unallocated, so the decision can be revised openly before registration. Preserve legacy codec behavior for historical checkpoints; simply changing the encoder underneath G0002 would invalidate its baseline identity.

Status: The code repairs in the preferred sequence are in. The 32K design was revised on 1 October 2026 and is not authorized. Question A keeps codec v3 with the native runtime. Question B uses codec v4 and the native runtime. G0005 is not allocated. No campaign script was added.

Code organization: a small consolidation, not a rewrite

The policy interface and Python/native differential approach are useful foundations. The main maintenance weakness is accumulated experiment machinery: A8Config inherits historical settings, phase1.py owns scheduling, four collection paths, optimization, diagnostics, milestones and recovery, and evaluation uses a training collector to obtain terminal state.

I would create two focused modules as part of the necessary work: one race executor taking an explicit coordinate and returning a typed outcome, and one training-state owner responsible for validation and durable checkpoint publication. Aggregate evaluation should reduce stored outcomes, and campaign scripts should compose these modules. Keep cheap evaluation free to skip training buffers. Replace loosely typed callbacks only where these changes touch them; avoid a broad framework or wholesale configuration rewrite.

The test lesson is equally important: shape, bounds and Python/native parity do not prove that a feature means what its name says. The current finish-distance test repeats the same incorrect arithmetic. Add a few independent examples based on race semantics: one lap remaining, different absolute speed limits, different revealed speeds, and interrupted save publication.

Status: Race coordinates and a typed race outcome live in the eval harness. Durable checkpoint publication lives in the training-state module. The new observation tests use race meaning rather than the old formula. No new framework was added.
