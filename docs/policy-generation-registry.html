Implemented · registry schema 1

Generation numbers make policy history readable.

Every comparison-worthy learned recipe receives one immutable chronological generation ID. Independent seeds remain runs within that generation, while a machine-readable manifest preserves the exact recipe and selected checkpoint identity.

01 · Stable identity

The ID describes chronology; the alias describes intent.

FormMeaningExample
G####One immutable resolved training recipe. The number is globally increasing.G0003 was created after G0002.
G####-R##One independent run of that recipe. For current campaigns the run number matches the seed number.G0003-R02 is generation 3, seed/run 2.
G####-R##@checkpointA particular milestone when the base run ID alone would be ambiguous.G0002-R00@1000K.
dev-*Disposable smoke or diagnostic policy that must not enter long-lived comparisons.dev-anchor-smoke-a.

Reports should pair the immutable ID with a short alias on first use—for example, G0003 (S2 fixed anchor)—and use the ID thereafter. Experiment labels remain useful descriptions, but they are not policy identities.

This namespace is only for learned policies. Fixed scripted rulers retain explicit versioned names such as heuristic_repaired and StaticSearchV1; a learned historical ruler is identified by its registered checkpoint ID.

02 · When the generation changes

Anything capable of changing learned weights creates the next generation.

ChangeIdentity actionReason
PPO/model hyperparameter, reward, observation/action representation, training track distribution, opponent mixture, initialization, parent, anchor, or meaningful trainer behaviourAllocate the next G####The resolved recipe is different.
Another seed or exact rerun of the same recipeAdd the next R## inside the existing generationIndependent evidence, unchanged recipe.
Additional checkpoint from the same runKeep the run ID; add an @checkpoint suffix when referencedSame learned trajectory.
Evaluation opponent, track band, sample size, or report changeNo training-generation changeThe policy weights are unchanged; the evaluation artifact records its own design.
Smoke or broken trialUse dev-*, or retain an already allocated ID with failed statusNever reuse an allocated number or rewrite history.
03 · Machine-readable provenance

The central index provides discovery; one immutable manifest describes each recipe.

experiments/policy_registry/
├── index.json      # chronology and next unused generation
├── g0001.json      # complete recipe plus registered runs
├── g0002.json
└── g0003.json

Each manifest records the full resolved training configuration, track generator parameters, policy contract, parent generation, anchor checkpoint identity, selection rule, source provenance, run seeds, selected checkpoint paths, byte sizes, and SHA-256 hashes. A canonical recipe hash detects silent edits.

Source of truth.The registry owns identity and recipe provenance. Files under runs/ remain generated artifacts and may keep historical filenames; moving or renaming a checkpoint is not what creates a generation.
04 · Campaign workflow

Register before compute, finalize hashes after selection.

  1. Allocate
    reserve the next G number
  2. Freeze
    resolved recipe and provenance
  3. Train
    use registered run IDs
  4. Select
    record checkpoint hashes
  • Before a full run.
    Add the index entry and manifest; capture the Git commit, whether the tree is dirty, and a saved patch plus SHA-256 when dirty. Record parents and input checkpoint hashes.
  • At launch.
    Use the registered G####-R## in log, checkpoint, and experiment metadata. Store the complete resolved configuration rather than relying on changing defaults.
  • After selection.
    Record the immutable selected checkpoint ID, path, size, and SHA-256. A later selection-rule change updates evaluation/selection metadata; it does not alter the recipe history.
  • In evaluation.
    Persist agent IDs and selected checkpoint IDs alongside paths. Human reports give the alias only as explanatory text.

New manifests use captured_clean provenance with a 40-character commit, or captured_dirty with that commit plus a saved patch and its SHA-256. The validator permits retroactively_reconstructed only for the G0001–G0003 backfill.

06 · Honest reconstruction boundary

Checkpoint identity is exact; old source provenance is incomplete.

The selected checkpoint paths, sizes, and SHA-256 hashes are verified. The training settings were reconstructed from A8's experiment record, logs, and preserved defaults. Those old campaigns did not save a clean Git revision and dirty patch at launch, so the manifests mark their source provenance retroactively_reconstructed. They must not imply code-level reproducibility that the original evidence cannot support.

Future requirementA new generation is not ready for a full campaign until its resolved recipe and source revision/patch evidence are recorded. This closes the only important provenance gap found during the A8 backfill.
07 · How the convention is remembered

AGENTS.md triggers the behaviour; code and tests detect drift.

The concise mandatory rule lives in repository-root AGENTS.md, which Codex reads whenever it works in this project. That is the correct place for the trigger. This document contains the detailed policy, and experiments/policy_registry/index.json is the machine-readable source of truth.

heat.ml.policy_registry.validate_registry verifies chronology, parents, unique run/checkpoint IDs, canonical recipe hashes, and—when requested—the selected checkpoint sizes and SHA-256 hashes. Focused tests exercise the full retroactive catalogue. Together these layers cover agent behaviour, human explanation, and mechanical integrity without duplicating the entire specification in the prompt.
