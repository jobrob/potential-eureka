Architecture selected - detailed A+C design written - 21 July 2026

Choose an architecture that can reach a useful 48-hour scale.

D2 taught us that HEAT's common rules can compile very quickly, but forcing every irregular game through one fixed masked schedule is slower than the scalar engine. The next step should be chosen by the scale we want, not by the size of the next convenient patch.

Direction D - post-D2 architecture decision
Detailed follow-up: options A and C implementation design · Evidence: D2 exact slice and compiled redesign

Recommended route Native exact CPU pool, then GPU.

Port exact game execution to compact C++ state, run independent games on native threads, and batch only at the PyTorch policy boundary. Add GPU inference and updates if the CPU pool can supply them.

01 - Decision in one page

The best balance is a native exact environment pool with a batched PyTorch boundary.

The current measured baseline produces about 233 million practical transitions in 48 hours. The old 600 million target requires 2.58x current trained throughput; a safer 800 million engineering target requires 3.44x. Inference batching alone cannot reach either target. We need to make exact rules substantially faster as well, and likely accelerate PPO updates if we want a credible route toward one billion transitions.

Primary direction Build each game as an independent, compact native state machine in C++. Execute only the branches that game actually needs. Run many games on a native thread pool. Return ready observations and legal masks in batches for the existing PyTorch policy. Keep Python events and rich objects outside the hot path. Preserve the current exact RNG contract at first.

Why this changed: the original tensor direction assumed that doing more rules as one tensor program would remove Python overhead. D2-R1 proved that for the uniform common core. D2-R2 then proved the harder point: fixed masked work for clutter, finish, stress, and replenishment can cost more than exact scalar branching. Native independent state machines keep the fast data-oriented representation without forcing finished or simple games to execute other games' branches.

Fallback: a synchronous multi-process PPO actor pool is the cheapest serious bridge and may just reach 600 million. It has too little margin to be the preferred 800 million design.

Escalation: if the native CPU pool cannot sustain at least 4,000 trained transitions/s, add GPU inference and PPO updates. If that combination still cannot sustain 5,000 transitions/s, consider the full device-resident rewrite. Change the learning algorithm only as a separate research decision.

05 - Direction A

Native exact CPU environment pool: independent games, shared inference batches.

Simple idea: translate the hot game state and rules into C++. Every game owns compact state and exact RNG. Native worker threads advance games independently until they need a policy decision. A ready queue gathers observations into a PyTorch batch. Python receives trajectory blocks and optional debug events, not one callback per rule action.

native game 1 --\
native game 2 ----> ready queue --> PyTorch policy batch --> actions
native game 3 --/          ^                                  |
      |                     +----------------------------------+
      +--> compact trajectory buffers --> Python PPO learner

Estimated 10 chunks

ChunkDeliverableGate
A0Freeze the native ABI, state capacities, error model, build route, and exactness receipt format.A minimal extension builds on Windows and round-trips a numeric receipt.
A1Compact native game/player/track/card state plus Python bridge.Exact D0 semantic snapshots for generated 2-6 seat states.
A2Representative hard slice: normal play, traffic, clutter, finish, replenishment, stress, reshuffle.At least 100,000 zero-mismatch transitions and at least 3x scalar slice speed.
A3Remaining gear, cards, react, movement, slipstream, corner, lap, and terminal rules.Full-race lockstep equivalence on a bounded randomized corpus.
A4Native observations, legal masks, rewards, and terminal rows.Exact arrays and event/reward ordering against Python.
A5Python-compatible MT19937 draw, shuffle, state save, and resume.Exact draw sequence and next-state parity under lane reorder and resume.
A6Native thread pool, per-game ownership, ready queues, backpressure, and bounded stop.Repeatable output with 1, 2, 4, 8, and 12 workers; no lane-order dependence.
A7Batched PyTorch inference boundary and compact trajectory transfer.No Python call per game step; useful p50 batch; fixed policy version per PPO collection.

Pros

  • Matches HEAT's branchy rules. Each game executes its actual branch rather than all masked branches in a fixed schedule.
  • Uses the current 16-core CPU. C++ threads can run exact games in parallel without Python's object and interpreter overhead.
  • Preserves the existing learning method. PPO, rewards, policy architecture, and evaluation remain unchanged.
  • Preserves useful D2 work. D2's fixed state, semantic snapshots, receipts, observation layout, legal masks, and randomized parity corpus become the specification.
  • Creates the right GPU feed. A ready queue can make batches without D1's Python bridge drain.
  • Supports exact segmented resume. Native state is explicit rather than hidden inside Python generators.

Cons

  • Large duplicate-rules burden. Every production rule now exists in Python and C++; differential testing becomes permanent infrastructure.
  • Native debugging is harder. Memory safety, build failures, crashes, and Windows ABI issues are more expensive than ordinary Python errors.
  • Exact Python RNG may constrain the design. Matching MT19937 shuffle and consumption order is safer for replay but not the fastest theoretical RNG.
  • The policy boundary can still bottleneck. Poor queue design or small ready batches could preserve too much Python/PyTorch overhead.
  • Maintenance cost is real. New game rules must be implemented and parity-tested twice.
First affordability gate Do not port the easy path alone. A2 deliberately includes the branches that defeated D2-R2. Continue only if that representative slice is exact and at least 3x faster than scalar. This should take roughly 1,000-1,800 lines and 2-3 working weeks; the benchmark itself should take less than one CPU hour.

Supporting sources: EnvPool uses a C++ batched environment pool with a thread pool and Python bindings, demonstrating the general architecture. The EnvPool paper reports that native parallel environment execution can beat Python subprocess designs across hardware scales. PyTorch documents custom C++ operators and its C++ extension API as supported integration routes. These sources support the pattern, not the HEAT performance estimate.

06 - Direction B

Synchronous multi-process PPO actors: cheapest route that might reach 600M.

Simple idea: keep the current exact Python engine. At each PPO iteration, freeze one policy version, send it to several worker processes, let them collect complete games independently, combine their trajectories, and perform one central PPO update. Workers do not continue under a new policy until the update is complete.

Estimated 6 chunks

  1. Freeze worker protocol, game identities, seed allocation, trajectory ordering, and failure rules.
  2. Implement one deterministic spawned actor and shared/frozen policy loading.
  3. Run three or four actors, aggregate trajectories, and reproduce scalar PPO inputs.
  4. Add bounded collection, backpressure, process health, timeout, and clean shutdown.
  5. Add exact segmented resume with worker-batch boundaries and deterministic result ordering.
  6. Run matched 1/3/4-worker throughput and one-hour soak gates.

Pros

  • Lowest semantic risk. The current Python game remains the only rules implementation.
  • Reuses measured machine behaviour. Three independent training workers previously achieved 2.703x aggregate throughput with about 95% per-worker retention.
  • Preserves synchronous PPO. All actors collect with one frozen policy, then the learner updates, matching PPO's collect-then-optimize structure.
  • Faster first answer. A bounded prototype can be measured before a native port is complete.

Cons

  • It may only scrape past 600M. A perfect 2.703x transfer would project about 629M; central coordination and trajectory transfer will reduce that.
  • Inference remains duplicated. Each process normally runs scalar or small-batch policy calls unless a second central-inference design is added.
  • Windows spawn and serialization are permanent costs. Large trajectory copies and repeated model distribution can consume the gain.
  • CPU and PyTorch threads compete. Worker count, Torch thread count, and learner work require careful fixed resource allocation.
  • Scaling beyond one machine adds infrastructure. Fault tolerance, networking, policy versioning, and observability become much larger concerns.
Adoption gate Prototype cost: about 500-900 lines and 3-5 working days. Production cost: about 1,000-2,000 lines and 2-4 weeks. Stop below 2.0x trained throughput. Treat 2.6x as a 600M bridge; require at least 3.2x before treating it as the long-term design.

Supporting sources: Ray's RLlib scaling guide describes independent environment-runner actors, vector environments per actor, and separate learner actors. The PPO paper describes alternating between data collection and multiple optimization epochs, which is the reason this option keeps a synchronized policy-version boundary. Ray is evidence for the pattern; adopting Ray itself is optional and may be unnecessary for a single Windows machine.

07 - Direction C

Native CPU actors plus GPU inference and PPO: the strongest 800M-1B path.

Simple idea: use Direction A's native workers to keep the CPU busy and continuously fill large observation batches. Copy compact batches through pinned host buffers to one GPU. Run inference there while CPU workers continue rules work. Keep PPO minibatches on the GPU as well. Double-buffer the ready and result queues so CPU simulation, data transfer, inference, and learning overlap where safe.

Estimated 7 additional chunks after Direction A

  1. Record actual GPU model, memory, driver, CUDA compatibility, and CPU/GPU transfer bandwidth.
  2. Install a compatible CUDA PyTorch environment and reproduce the CPU policy numerically.
  3. Add reusable pinned observation/action/trajectory buffers and explicit ownership.
  4. Benchmark GPU inference across collector-supplied batches, not synthetic large batches alone.
  5. Move PPO update tensors and optimizer state to GPU; re-prove resume and checkpoint identity.
  6. Overlap CPU simulation, non-blocking transfers, and inference with double buffering and backpressure.
  7. Run end-to-end matched benchmarks, thermal soak, memory checks, and an eight-hour rehearsal.

Pros

  • Attacks the remaining two large components. Native CPU speeds rules; GPU batches speed inference and potentially the 10.24-second PPO update.
  • Has a credible one-billion model. Batched inference plus 5x rule speed and 2x update speed models about 1.02B practical transitions.
  • Retains exact CPU rules. GPU numeric differences affect policy computation, not game legality or chance outcomes.
  • Can be added after evidence. The native pool must first prove it can supply useful batches, avoiding premature CUDA work.

Cons

  • Hardware is currently unknown. The installed PyTorch is CPU-only; a suitable GPU has not been confirmed.
  • The policy may be too small for GPU efficiency. Small models and small batches can be dominated by transfer and launch overhead.
  • Overlap adds concurrency complexity. Buffer lifetime, streams, synchronization, and policy-version boundaries must be explicit.
  • CUDA changes the operational environment. Drivers, wheels, deterministic kernels, memory pressure, and checkpoint portability need new receipts.
  • GPU inference can starve. Without enough native games, waiting for large batches reduces rather than improves throughput.
Entry and adoption gates Enter only after the native pool sustains useful ready batches and after an explicit hardware receipt. Continue if GPU inference improves the full collection loop by at least 1.25x. Adopt the combined design at 5,000+ trained transitions/s with under 5% repeat spread; target 6,500/s if one billion is the goal.

Supporting sources: PyTorch's CUDA semantics documents asynchronous execution, pinned memory, and non-blocking copies that can overlap CPU and GPU work. Its performance tuning guide explains inference and GPU optimization, including the cost of CPU launch and synchronization. The Torch-TensorRT guide explicitly warns that very small models and batch size one can be slower because bridge and launch overhead dominate, which is why collector-supplied batch size is a hard gate.

08 - Direction D

Full device-resident JAX or PyTorch rewrite: highest ceiling, highest rewrite risk.

Simple idea: replace the Python-compatible execution contract with an explicitly versioned array engine designed for accelerators. Keep all game state, random keys, rule control flow, observations, policy inference, trajectory storage, and possibly PPO updates on one device. Use structured conditionals and loops instead of a fixed six-turn masked schedule.

Estimated 12 chunks

  1. Decide whether this is a new engine semantic version with a new RNG contract.
  2. Freeze bounded device state, capacities, overflow rules, and compact receipt schema.
  3. Implement counter-based per-game RNG and deterministic key allocation.
  4. Implement structured control flow for gear and cards.
  5. Implement movement, traffic, corners, slipstream, finish, and terminal rules.
  6. Implement replenishment, stress, reshuffle, and rare branches.
  7. Implement device observations, legal masks, rewards, and trajectory rows.
  8. Implement a device-resident scheduler and bounded rollout boundary.
  9. Integrate policy inference without host round-trips.
  10. Integrate PPO updates and checkpoint/resume.
  11. Run exact semantic checks where contracts overlap, plus distributional equivalence for the new RNG.
  12. Run scaling, memory, learning-equivalence, soak, and failure-recovery gates.

Pros

  • Highest single-machine ceiling. It can remove most Python, host/device transfer, and small-kernel launch boundaries.
  • Counter-based RNG fits parallel lanes. Game identity can determine random keys without shared consumption order.
  • Structured device control flow can avoid D2-R2's fixed schedule. A compiled loop or conditional can execute one selected branch while preserving fixed state shapes.
  • One representation serves the full loop. Rules, observations, inference, trajectories, and learning can remain on the accelerator.
  • Best path to future multi-device scale. Explicit array state is easier to shard than Python objects.

Cons

  • It may abandon bit-for-bit historical replay. A new counter-based RNG will not reproduce Python MT19937 shuffle sequences.
  • Every uncertainty moves at once. Rules, RNG, control flow, device compiler, training loop, and hardware all change.
  • Parity becomes more subtle. Exact rule semantics can match while stochastic trajectories differ; distributional tests and new policy generations are required.
  • Windows support and compilation must be proven early. JAX or an alternative compiler may add installation and debugging friction.
  • Learning changes may be hard to attribute. A speed win is not enough if new random streams or numerical choices change training behaviour.
  • Large sunk-cost risk. This is likely 5,000-10,000 lines and 10-18 weeks before a production answer.
When this becomes justified Choose this if Direction A plus C cannot sustain 5,000 trained transitions/s, or if future requirements clearly exceed one billion transitions on one machine. The first spike should implement the hard D2-R2 branches with structured device control flow and the proposed new RNG. Stop if it cannot beat scalar by 3x without host callbacks.

Supporting sources: the JAX PRNG design explains counter-based functional keys that are reproducible, vectorizable, parallel, and scalable. JAX's structured control-flow documentation and while-loop primitive show how dynamic rule control flow can be lowered to compiled operations while state keeps fixed shapes. These mechanisms are technically relevant, but only a HEAT spike can show whether the branch structure is fast enough.

09 - Direction E

IMPALA/V-trace or asynchronous PPO: remove the collect/update barrier.

Simple idea: let actors continue producing experience while the learner updates. Because actor policies can lag behind the learner, use an algorithm designed to correct off-policy experience, such as IMPALA's V-trace, or adopt a carefully specified asynchronous PPO variant. Scale actors and learners independently.

Estimated 10 chunks

  1. Write a separate learning-method design with exact policy-lag and correction semantics.
  2. Add behaviour-policy logits, values, discounts, bootstrap rows, and policy versions to trajectories.
  3. Implement actor queues, backpressure, batching, health, and restart behaviour.
  4. Implement and reference-test V-trace or the selected asynchronous objective.
  5. Implement learner batching and policy publication.
  6. Define maximum policy lag, sample rejection, and stale-actor recovery.
  7. Define deterministic run identity, checkpoint, queue, and resume semantics.
  8. Run toy/reference correctness tests and short HEAT learning smokes.
  9. Run matched sample-efficiency and skill comparisons against frozen PPO.
  10. Only then run throughput scaling and a bounded stability pilot.

Pros

  • Actors and learner no longer wait for each other. Collection and optimization can overlap continuously.
  • Scales beyond one machine. More actor processes or hosts can be added without one global rollout barrier.
  • Handles stragglers better. One slow game or worker need not stop the entire iteration.
  • Pairs well with native actors. It can become a later scaling layer once environment execution is efficient.

Cons

  • This is a new learning algorithm. Existing PPO evidence, hyperparameters, and policy-generation conclusions do not transfer automatically.
  • More transitions may buy less learning. Off-policy correction and stale actors can reduce sample efficiency even while wall-clock throughput rises.
  • It does not fix slow rules. The current Python environment still limits how much one 16-core machine can produce.
  • Resume becomes much harder. In-flight queues, actor policy versions, rejected samples, and learner state must be defined.
  • Evaluation needs a new generation. This cannot be treated as an implementation-only Direction D change.
Use only for a different bottleneck Open this direction if native collection becomes fast enough that the synchronized PPO barrier or multi-machine scaling is the measured limit. Require learning at least as strong per wall-clock hour as frozen PPO, not merely more transitions per second.

Supporting sources: the IMPALA paper introduced decoupled actors and learners with V-trace correction and demonstrated high-throughput distributed learning. Ray's current architecture documentation separates environment runners from learners, and its scaling guide exposes both axes. This supports the scalability claim, not equivalence to HEAT's current PPO recipe.

10 - Direction F

Learned simulator: valuable research, but not a substitute for exact transitions.

Simple idea: train a model to predict the next state or latent state, rewards, chance outcomes, terminal flags, and possibly legal actions. Use it for cheap imagined rollouts, policy pretraining, or search. Keep the exact engine authoritative for real training data and evaluation.

Estimated 12 chunks

  1. Define dataset, visibility, chance, and policy-generation provenance contracts.
  2. Generate and validate exact transition sequences with adequate rare-branch coverage.
  3. Choose observable-state or latent-state architecture and stochastic objective.
  4. Build exact legality and chance interfaces around the learned component.
  5. Train a one-step baseline and calibrate stochastic predictions.
  6. Measure multi-step rollout error by phase, seat count, track, and rare branch.
  7. Measure policy-value and action-ranking distortion, not prediction loss alone.
  8. Build bounded imagined-trajectory generation with uncertainty cutoffs.
  9. Choose search, pretraining, or data-augmentation integration; do not mix all three first.
  10. Run exact-environment skill attribution against a fixed data budget.
  11. Study exploitability and model-error feedback loops.
  12. Only then consider production use behind an explicit approximate-data label.

Pros

  • Imagined steps can be extremely cheap. A neural model can batch thousands of hypothetical continuations.
  • Can support search. Cheap rollouts may improve action selection even if they never replace real training games.
  • Can focus exact computation. Uncertainty can decide when to return to the real engine.
  • Offers a path beyond hardware limits. It changes the cost of experience instead of only optimizing execution.

Cons

  • Imagined transitions are not the 600M/800M exact target. They cannot be counted as equivalent evidence.
  • HEAT is difficult to model. Private hands, deck uncertainty, simultaneous choices, traffic, and rare rule branches create multi-modal futures.
  • Small errors compound. A model can have good one-step loss and still produce strategically false long rollouts.
  • The policy can exploit model errors. Training may improve in the simulator while becoming worse in exact games.
  • It is the largest research uncertainty. Data generation, model design, learning integration, and exact evaluation all need separate gates.
Keep it separate This direction is worthwhile only as a named research programme. Do not use it to declare the exact 48-hour substrate complete. The first useful question is whether a learned model improves exact-environment skill per wall-clock hour when used for one bounded purpose, such as search.

Supporting sources: MuZero demonstrates planning with a learned model across board games and Atari without being given the environment dynamics. DreamerV3 demonstrates policy learning from imagined trajectories across many domains. They establish that learned models can support strong planning and control; neither is a close analogue for HEAT's private information, simultaneous choices, and exact stochastic replay. A separate learned-dynamics design should therefore perform a focused literature review before choosing an architecture.

11 - Hardware and scale-out

Hardware is a multiplier, not a replacement for the right execution model.

The current baseline came from a 16-logical-CPU Windows machine with a CPU-only PyTorch wheel. Three hardware changes are possible, but each needs the software architecture that can use it:

Hardware moveHelps which directionBenefitLimit
More CPU cores on one machineNative pool or process actorsMore exact games can advance in parallel with shared memory.Memory bandwidth, inference, and PPO updates eventually dominate.
One suitable GPUNative + GPU or device rewriteFaster batched inference and updates; possible overlap with CPU rules.Small policy/batches may not amortize transfer and launch cost.
Multiple machinesActor/learner architectureHighest actor scale and fault isolation.Network, stale policies, orchestration, exact resume, and cost become first-class problems.

Buying or renting hardware before the first native slice is unlikely to answer the central question. The code must first show useful per-core efficiency and supplyable inference batches. Once those are measured, a short cost model can compare engineering time with a CPU upgrade, GPU upgrade, or rented multi-core host.
