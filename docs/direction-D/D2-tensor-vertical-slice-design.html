D2-R stopped after exact R2 missed the CPU speed gate - 20 July 2026

D2: turn the exact slice into one compiled numeric step.

The first D2 implementation proved exactness but ran about nine times slower than scalar. D2-R proved that a compiled common core can be fast, then stopped when the complete non-reshuffle rules fell to 0.839x scalar speed. Exact RNG work was not started.

Direction D - implementation design
Decision source: two ways forward after D1

Boundary Exact implementation retained; expansion stopped.

R0, R1, and R2 are implemented. R2 is exact across 10,240 transitions but too slow, so R3-R6, CUDA training, a full tensor race, and learned-policy work remain unstarted.

01 - Goal

Answer one question before rewriting more rules.

Can Heat's exact rules run well as batched tensors? D2 should answer this with one complete path through real state, legal actions, random draws, movement, and the next policy decision.

Simple rule: correctness comes first. A fast result with one unexplained state, observation, legal-action, reward, or random-draw difference is a failure.
02 - The vertical slice

Start with cards and finish at the first react decision.

The representative slice begins with legal card choices ready for every active seat. It applies those card choices, reveals speed, moves the cars, applies automatic adrenaline, and stops when the first real react decision is ready.

This slice is useful because it touches private hands, card state, random stress draws, track geometry, traffic, movement, turn order, observations, and legal actions. It is large enough to teach us whether tensors fit the game, but much smaller than a full race.

Gear selection is implemented first as a simpler proving step. The cards-to-react slice is the real D2 result.

04 - D2-R redesign

Make the entire hot slice one compiled numeric program.

Do not tune the eager kernel or merely raise its batch size. Its work is still almost linear per game. Rebuild the cards-to-REACT boundary as a pure function with fixed numeric inputs and outputs, then require torch.compile(fullgraph=True) to capture the whole operation without returning to Python.

Selected route: retain PyTorch and the exact D2 tensor contract, but replace Python-led lane execution with one compiled, functional step. This follows the successful Pgx and JaxMARL shape while avoiding a second JAX runtime beside the existing PyTorch policy. A native CPU kernel is the hard fallback if the first full-graph feasibility gate fails.

These examples do not justify a promised speed-up. They identify a shared implementation shape: large batches help after the complete hot operation is compiled or native. The original D2 had tensor storage, but its Python control flow, scalar reads, event objects, and many tiny tensor operations prevented that shape.

The compiled boundary

  • Fixed numeric state: preserve the existing bounded tensors for 2-6 seats and generated tracks. Capacity overflow remains an explicit error.
  • Pure functional update: inputs determine all outputs. No mutation of Python game objects, callbacks, strings, dictionaries, global RNG, or hidden caches.
  • No scalar escape: no per-lane .item(), .tolist(), Python bool, or Python list construction inside the compiled function.
  • Numeric receipts: events use fixed integer codes, numeric fields, a fixed-capacity buffer, and a length per game. Canonical Python event objects are reconstructed outside the hot path for parity tests, debugging, and UI consumers.
  • Exact random state: each lane retains an independent stream. D2-R may not silently replace Python's random sequence with a statistically similar generator.
  • Stable observations: keep the already-fast tensor observation and mask logic inside the compiled result rather than redesigning its semantics.

D2-R5 - Measure compiled scaling and training value

Benchmark batches 1, 8, 32, 64, 128, 256, 512, and 1,024. Separate first compile time, warm compiled execution, numeric receipt generation, optional Python event materialization, bridge work, and memory. Use the frozen D1 timing model for the end-to-end estimate.

Only after D2-R5 passes, write the D4 experiment boundary for batches such as 1,024 and 4,096 with environment state, observations, policy inference, and rollout tensors kept on one device. CUDA installation, GPU measurement, and training remain separate permission-gated work.

06 - Correctness strategy

Determinism is a required gate.

The tensor engine must not merely produce a valid game. Given the same state, actions, and random inputs, it must produce the same game as the legacy engine. Packing a game into a batch must not change it.

Test 1 - State and observation parity

Convert legacy states into tensors and compare them using the existing D0 semantic snapshot. Compare observations with exact array equality and compare every legal-action mask bit. Cover 2-6 seats, generated track limits, empty and full card piles, heat, finished cars, and spun cars.

Implemented. Round-trip, capacity, 2-6 seat, generated-state, observation, and legal-mask tests use exact equality and reject overflow rather than clipping it.

Test 2 - Lockstep rule replay

  1. Create or capture one exact legacy state.
  2. Convert it to tensor state.
  3. Give both engines the same legal actions and random draw inputs.
  4. Compare state after every internal step, not only at the end.
  5. Compare events, observations, masks, and next random state. Compare rewards and terminal flags once the tensor path produces complete transitions in D3.

For the D2 slice, comparison points include chosen cards, each stress draw, revealed speed, movement, automatic adrenaline, and the first react decision.

Implemented for the D2 boundary. An opt-in trace compares scalar and tensor state after chosen cards, every stress resolution, speed reveal, movement, adrenaline, and the resulting REACT row. This test found and fixed a turn-start position/lap ordering difference. Rewards and terminal-transition flags are explicitly deferred because this slice ends at REACT and does not yet emit a complete environment transition.

Useful safety checks

Also check simple invariants such as card conservation, unique card identities, valid track positions, legal masks that contain an action when a decision is required, and valid finish order. These help locate failures, but they do not replace direct comparison with the legacy engine.

Implemented. Dedicated checks cover card conservation, per-player card identity uniqueness, position bounds, consecutive finish order, nonempty masks at decision points, and clear capacity rejection.

D2-R compile-specific checks

The redesign adds structural tests that the eager implementation did not need: full-graph capture must succeed; compile/recompile counts must stay within the frozen-shape contract; numeric receipts must round-trip to exact canonical events; overflow must fail; and source checks must reject scalar escapes or Python object construction inside the compiled module. These checks supplement semantic comparison rather than replacing it.

Boundary: D2-R must re-prove exactness for its compiled vertical slice. Full-race determinism remains the main D3 gate before any tensor engine can replace the legacy rules path.

08 - Current decision

D2-R stops before exact RNG because complete deterministic rules are slower than scalar.

  • CONTINUE D2-R.
    D2-R1 has zero graph breaks and semantic differences, is at least 10x faster than eager D2, and reaches at least scalar speed at batch 256.
  • ADOPT FOR D3.
    The completed D2-R has zero differences, at least 3x kernel speed at a supplyable batch, and at least 1.5x projected end-to-end training.
  • NATIVE FALLBACK.
    Full-graph compilation fails, exact RNG erases the gain, or only unsupplyable batches are fast. Keep scalar as default and design a bounded native CPU comparison.
Current decision - STOP D2-R AT R2: R0 receipts and the R1 common core passed. R2 also stayed exact and full-graph, but its 0.839x scalar speed failed the frozen affordability floor. Keep scalar as the production default and retain compiled R0-R2 as measured reference code. Do not begin R3 exact RNG, R4-R6, D3 implementation, CUDA work, a learned-policy campaign, or a large compute run without a new design decision. See the expanded architecture comparison for the proposed native-first route and the larger alternatives.
