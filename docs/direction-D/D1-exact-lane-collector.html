02 - Implementation decision

Add an opt-in lane collector over the existing engine.

The first D1 implementation is a LegacyLaneEnvironment. Each lane owns one ordinary GameState and run_round_driver generator. A scheduler exposes at most one live policy decision from each lane, orders rows by stable game identity, performs one policy inference call, and sends each decoded action back to its own generator.

Why this is the right first slice. It creates useful cross-game batches without a second rules implementation. The same collector can later consume the D2 tensor environment through the D0 protocol, so D1 is production architecture rather than a disposable benchmark hack.

03 - Frozen invariants

Scheduling may change; transition semantics may not.

  • Stable identity.
    Every live choice is identified by (game_id, seat_id, decision_index). Ready rows are deterministic and an identity can be applied only once.
  • One open span.
    A game-seat has at most one recorded action awaiting its next live decision or terminal state.
  • Exact reward span.
    Reward is measured from the state in which the seat acted to that seat's next live choice, termination, or truncation, using the existing A8 reward functions.
  • Simultaneous secrecy.
    Gear and card choices remain unapplied until the engine has received every seat's choice. Cross-game batching must not expose another seat's action.
  • One policy version.
    All recorded and bridge actions used to close a rollout are sampled before the PPO update. A lane never carries an old-policy sample across an update.
  • Per-stream GAE.
    GAE is computed independently for each game-seat fragment, with zero bootstrap on true termination and a value bootstrap at a nonterminal cut or time-limit truncation.
04 - Bounded rollout cut

Record exactly the target number of actions, then drain only those spans.

Finishing every live game would multiply scalar overshoot by the lane count. D1 instead admits recorded actions in stable row order until exactly n_steps have been admitted. It then enters drain mode. The frozen policy may still choose short-lived bridge actions needed to advance the engine, but those bridge actions are not added to the PPO batch.

The collector stops as soon as every pre-cut recorded action has received its reward and successor observation. Any bridge spans still open belong to lane objects that are discarded before the update. This preserves one policy version, gives every retained sample a valid bootstrap boundary, and bounds overshoot independently of the number of lanes.

Resume boundary. D1 continues to checkpoint only after the collector has drained, PPO has updated, pool maintenance and callbacks have completed, and D0's atomic training-state write can run. Mid-rollout lane serialization remains out of scope.

06 - Correctness gate

No throughput benchmark runs before these checks pass.

  • Fixed-action single-lane traces match the scalar oracle at every live decision and at terminal state.
  • Mixed 2-6-seat lanes keep game, seat, and decision identities isolated and deterministic.
  • Every recorded action completes exactly once with the same reward, done flag, successor observation, and legal mask as scalar collection.
  • A cut inside a game produces the same per-stream advantages as an equivalent scalar fragment, including nonterminal and truncation bootstraps.
  • Policy-version mismatch, duplicate/stale identity, illegal action, incompatible resume recipe, and corrupt checkpoint all fail before unsafe continuation.
  • Focused D0, D1, A8, Ruff, and strict mypy checks pass.

08 - Live status

D1 implementation is complete, but the performance branch stops here.

Final go/no-go: STOP. Correctness, batch size, bounded runtime, and zero retained overshoot passed. End-to-end throughput did not: the best stable arm was 1.118x, below the frozen 1.3x stop threshold and well below 1.5x adoption. Keep the lane code as an opt-in diagnostic and as a tested environment/trajectory seam; do not make it the default, do not tune again on this inspected workload, and do not begin D2 automatically from this result. The next-step design compares a smaller synchronous CPU-worker route with the longer-term tensor-engine slice.
