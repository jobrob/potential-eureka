Diagnostic complete - eager PyTorch design closed - 20 July 2026

D2 profiling: batching never removed the per-game work.

The tensor state is exact, but the CPU kernel still performs hundreds of small tensor and Python operations for every game. Larger batches therefore multiply work instead of turning it into a few efficient compiled operations.

Direction D - profiling report
Input: D2 correctness and Chunk 6 benchmark

Conclusion Do not tune the current eager kernel.

A credible D2 retry must be compiled and numeric end to end, or replaced by a native CPU kernel.

01 - Plain answer

The slowdown is structural, not one bad helper.

State copying, validation, observations, and masks are not the main problem. Almost all elapsed time is inside the rule kernel, where Python loops, event strings, individual tensor indexing, and tensor-to-Python reads still happen once per game.

Observation and mask work rises from 1.6 ms at batch 1 to only 3.8 ms at batch 256. That is successful vectorisation. The rule kernel rises from 3.8 ms to 214.4 ms, which is close to adding more individual game work. At batch 256 the kernel is 98.0% of the full-slice time, while clone and validation are about 1.0% and 0.1% respectively. Isolated component timings can overlap and contain normal measurement noise; they identify scale, not an additive decomposition.

Conversion takes 463.8 ms at batch 256, but it is not the root adoption blocker. A permanent tensor engine could avoid repeated conversion; it cannot avoid the slow rule kernel.

The per-game figures barely change when the batch grows fourfold. This is the opposite of successful vectorisation: the implementation stores state in tensors, but repeatedly selects one scalar from those tensors and returns to Python.

In the instrumented batch-256 Python profile, zone-to-string display construction alone used 31.2% of self time. Replenishment used 11.6%, card appends 7.3%, raw tensor .item() calls 6.5%, turn-start event construction 7.1%, play-card event construction 5.6%, and creating small tensors 2.8%. These are directional profiler shares; profiler overhead means they should not be treated as production wall-clock measurements.

A bounded torch.compile(fullgraph=True) probe failed at the first data-dependent validation expression, bool(torch.all(valid)). Even after removing that check, the kernel contains many more data-dependent Python branches, lists, strings, random-state objects, and scalar reads. Compilation is therefore a redesign, not a decorator change. PyTorch's own guidance explains that data-dependent control flow and Python built-ins create graph breaks and lose optimisation opportunities.

06 - Why Heat differs

The data type is not enough; the execution boundary matters.

Small scalar referenceThe legacy card-to-REACT slice is already extremely cheap. Tensor setup and dispatch have very little arithmetic to amortise.
Branch-heavy exact rulesStress, shuffles, replenishment, traffic, corners, finish order, and variable card identities produce data-dependent paths.
Python receipts inside the kernelExact events contain strings, dictionaries, card displays, and Python tuples. Successful compiled systems keep the hot step numeric.
Python-owned randomnessExact reshuffles restore and update individual Python RNG states, taking lanes out of one compiled numeric graph.
Eager CPU operationsEach select, scalar read, small tensor creation, and indexed write is dispatched separately. There is no JIT fusion.
A narrow sliceOnly one short phase-to-decision path is processed per call, so state and dispatch overhead are paid frequently.

Batch 256 was enough to expose this shape: throughput had already flattened around 1,150 games/s. Trying batch 1,024 with the same near-linear operator counts would mainly consume more memory and time. The published 1,024-16,384 configurations become useful only after the complete step is compiled or native.

07 - Decision

Close eager D2; retain the oracle for a fundamentally different kernel.

  1. Do not spend time tuning clone, validation, observation, or mask code. Together they are far too small to bridge the gap.
  2. Do not try larger eager batches or move this kernel unchanged to CUDA. The per-game host work and graph breaks remain.
  3. A compiled D2 retry must first prove one pure numeric step. No Python events, strings, lists, .item(), .tolist(), or Python RNG inside the compiled boundary.
  4. Use compact numeric event and RNG receipts. Materialise readable events only outside the hot path when diagnostics require them.
  5. Make the compiled unit coarser. Process a complete forced sequence or round so validation and dispatch are amortised.
  6. Gate before restoring full semantics. A stripped compiled/native prototype at batches 64 and 256 must first exceed scalar and show a credible route to 3x. Then reapply the D2 differential oracle.
Recommended implementation order: run the lower-risk three-worker complete-game prototype next. In parallel planning, compare a native data-oriented CPU kernel—Numba/Cython/Rust/C++—with a pure JAX or fully compilable PyTorch spike. The current exactness suite is the common acceptance gate for either kernel.
