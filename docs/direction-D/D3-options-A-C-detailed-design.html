01 - Decision and status

Design for the 800 million target, with one billion as the stretch target.

The implementation should favour throughput when a convenience choice and a performance choice conflict, but it must not trade away exact game rules, bounded failure, or safe resume. The native engine is a training-only second implementation; the Python engine remains the readable source of truth and the differential oracle.

Chosen design Use compact C++ game slots, one owner at a time per game, and fixed-capacity native arenas. Workers advance only the branches their games need. They stop at real policy choices, where Python/PyTorch evaluates many ready rows together. Forced choices, rules, observations, masks, rewards, and game RNG stay in native code. Python sees batches, completed trajectories, compact receipts, and errors - never one callback per rule action.
Adoption target5,000+/strained transitions end to end
Engineering target800Mpractical transitions in 48 h
Stretch target6,500/scredible route to one billion
Semantic toleranceZerounexplained engine mismatches

Decisions frozen by this document

  • Option A comes first. Option C reuses A's pool, state, batching protocol, trajectories, exactness corpus, and operational controls.
  • C++ is the native language. The production hot loop does not use Python objects, LibTorch, or a Python callback from a worker.
  • The native package is separate. Normal pip install -e ".[dev]" remains available without a compiler. Native development installs an additional local package.
  • Game RNG remains CPython-compatible MT19937. A game restored from the same Python RNG state must draw and shuffle identically.
  • Policy sampling becomes identity-keyed. A logical decision receives the same categorical draw regardless of worker count, queue timing, or batch order. This is distribution-equivalent but training-affecting, so the first non-smoke campaign needs a new registered policy generation.
  • Synchronous PPO remains unchanged. One policy version collects the whole iteration; the learner updates only after the native pool is drained.
  • Production does not materialize Python events. Numeric receipts are available for differential testing; event materialization stays outside the hot path.
No user choice blocks design work. This document follows the parent recommendation to preserve Python game RNG and engineer for 800M rather than the bare 600M line. The policy-sampling change is called out because it must be accepted as part of the later implementation entry gate, not because a choice is needed to understand the architecture.
02 - Performance contract

The target leaves almost no room for a merely tidy native port.

The D0 matched workload recorded 121,386 transitions in a median 81.11 seconds. At 5,000 transitions/s the same work must finish within 24.28 seconds; at the exact 800M rate of 5,144/s it must finish within 23.60 seconds. A should therefore be designed around the stronger 5x rules target, not only its 3x continuation gate.

These are allocation budgets, not independent acceptance tests. The measured full loop decides adoption. A component may exceed its line if another component creates enough real end-to-end margin.

Performance rules for implementation

  • No allocation in the per-decision native hot path. Game slots, queue nodes, ready rows, action results, receipts, and trajectory blocks are reserved before collection.
  • No exported C++ STL container or raw state pointer. Python sees an opaque pool plus versioned numeric buffers.
  • No full-state clone per transition. Pending reward state stores only the previous fields the reward calculation actually reads.
  • No dense 516-byte legal mask in long-lived native trajectories. Store nine 64-bit words; expand only where inference or PPO needs a boolean mask.
  • No default debug logging in production. Counters and optional receipt hashes are cheap; full receipts are a verification mode.
  • No fast-math. Exact observation and reward arithmetic is more important than speculative floating-point compiler gains.

04 - Native build and boundary

Keep the rule engine independent of the installed PyTorch wheel.

The proposed package is native/, installed separately as heat-native. It builds one pybind11 module named heat_native._core. The A implementation exchanges NumPy-compatible buffers and has no LibTorch link. This makes the same native engine usable from the current CPU-only environment and a later CUDA environment, provided Python and the extension ABI match.

Windows build route Use the discovered Visual Studio MSVC toolchain and an ahead-of-time setuptools/pybind11 build. Release uses C++20, /O2, /GL, /LTCG, /EHsc, /DNDEBUG, and precise or strict floating point. Debug uses bounds/assertion checks and symbols. The first chunk proves both builds before rules are ported.

Boundary rules

  • The exported object is an opaque NativePool; C++ struct layouts are not an external ABI.
  • protocol_version, state_schema_hash, codec_version, capacities, compiler identity, build type, and source identity are queryable and written into every receipt.
  • Input arrays require exact dtype, shape, contiguity, and writeability. Bindings reject mismatches rather than silently force-casting or copying.
  • Calls that wait for or execute native work release the Python GIL. Only buffer creation and Python object construction hold it.
  • NumPy/Torch views are leases. Each carries a generation token; submitting or releasing a stale token is a hard error.
  • The extension owns and joins every worker thread. No detached thread may outlive NativePool.close().

Minimal Python-facing surface

pool = NativePool(config, bound_buffers)
pool.admit(game_manifest)                  # bulk, iteration policy map frozen
ready = pool.wait_ready(max_rows, timeout_ms)
pool.submit(ready.token, actions, logps, values)
completed = pool.finalize_iteration()      # canonical compact trajectory views
receipt = pool.stats()
pool.close(timeout_ms=...)

The exact names may change during A0, but the number and granularity of boundary crossings should not. Fine-grained getters or setters are forbidden from the production path.

05 - Compact exact state

Use one cache-friendly game slot, not a tensor lane and not Python objects.

D2's TensorGameState remains the field checklist and bridge oracle, but its all-int64 tensor representation is not the production native layout. Each C++ game has a fixed-capacity, game-local structure. The worker reads and writes adjacent memory and follows ordinary branches. Output observations and trajectories use structure-of-arrays because the policy consumes rows.

Schema policy

  • The schema hash covers all capacities, numeric codes, observation/action dimensions, codec version, phase order, card-token rules, RNG version, receipt version, and struct-serialization version.
  • Capacity overflow is never truncated. It produces a typed error with the logical game, phase, player, observed count, and limit.
  • Checkpoint files never dump raw C++ struct bytes. They use named/versioned numeric arrays or, at the normal safe boundary, store no in-flight game state at all.
  • Track and card metadata can be interned within one pool only after byte-for-byte descriptor equality; game logic never relies on Python object identity.
06 - Exact state machine

Replace the Python generator with an explicit resumable program counter.

Each game advances through the same nine phases as run_round_driver. The native program counter records the phase, the player/turn-order cursor, and any substage needed to resume after a policy decision. A call to advance() runs forced and deterministic work until one of four boundaries is reached.

BoundaryMeaningNext owner
READY_GROUPOne or more real choices share a consistent pre-action state.Policy coordinator
BOOTSTRAP_READYA truncated game needs terminal value rows before final rewards close.Policy coordinator value-only path
COMPLETEEvery pending policy seat is closed and the game can be finalized.Trajectory finalizer
FAULTEDA capacity, legality, invariant, or internal error stopped the game.Trainer error path

Decision-group rules

  • GEAR and CARDS expose all non-forced seats from the same unapplied state, matching simultaneous-decision semantics.
  • REACT, SLIPSTREAM, and DISCARD expose the exact sequential choice at the point the Python driver yields it.
  • A forced or one-legal-action decision is resolved in native code and never becomes a PPO row.
  • A group has a stable token (game_id, decision_epoch). The action submission must cover every row exactly once and must pass legality revalidation before mutation.
  • Actions inside a simultaneous group are applied in the Python oracle's stable seat order, even though their policy evaluation was batched.
  • Every real live-policy choice first closes that seat's previous pending transition, then opens a new one from the current observation/action/logp/value.

Hard-slice boundary

The first performance slice is deliberately not the easy path. It contains two in-place fragments:

  1. Cards to first REACT: ordinary cards, clutter, already/newly finished players, stress chains, discard replenishment, empty-draw reshuffle, and exact RNG advancement.
  2. Movement to next decision: traffic, lap crossing, finish ordering, adrenaline/boost effects, slipstream, corner heat, spin-out placement/stress, discard, and replenishment.

Together these cover the irregular work that defeated D2-R2 before the complete native engine is affordable.

07 - Native pool and scheduler

Keep workers independent, but make admission and results independent of thread timing.

Each slot moves through a small checked lifecycle. Only the worker that successfully claims RUNNABLE may mutate the game. The coordinator is the only owner of ready-buffer leases and action submission. Completion order is never training order.

EMPTY -> RUNNABLE -> RUNNING -> READY -----------+
                    |          ^                |
                    |          +-- action ------+
                    +-> BOOTSTRAP_READY -> RUNNABLE
                    +-> COMPLETE -> FINALIZED -> EMPTY
                    +-> FAULTED  -> pool-wide bounded stop

Queue design

  • Begin with bounded preallocated queues guarded by a short mutex and condition variable. This is easier to prove correct than a custom lock-free queue and should be adequate at HEAT's decision rate.
  • Queue wait, wake, and contention time are measured from the first implementation. Replace with sharded or ring queues only if scheduling is more than 5% of rule-side time after the native rules pass.
  • Workers do not spin while waiting. The benchmark may test a short spin-then-park policy only after the blocking baseline.
  • Ready groups are never split across inference buffers. Rows within a buffer are sorted by logical identity for stable receipts and efficient scatter.
  • Backpressure is explicit: when every ready buffer is leased, workers publish no more rows and park without overwriting memory.

Deterministic iteration manifest

At the start of an iteration, Python freezes the seat count, live policy version, selected snapshot/anchor policy, and a deterministic list of game specifications. The number of games is estimated from a checkpointed rows-per-game average for that seat/opponent mode. Every manifested game is completed; if the result is short of n_steps, a deterministic top-up manifest is appended. This avoids a thread-race deciding which game crosses the collection threshold.

  • game_id is a monotonic campaign identity, not a slot number.
  • Episode seed and generated track are pure consequences of the manifest and the existing training namespace.
  • The rows-per-game estimator and next game ID are training state. Resume restores both.
  • All completed rows are canonicalized by (game_id, seat_id, decision_sequence) before PPO. Worker completion order is telemetry only.
  • The initial estimate comes from a measured scalar receipt; later estimates use a fixed-form exponential moving average. The formula and coefficient are recipe fields.

Worker count policy

Do not hard-code 15 workers because the machine reports 16 logical CPUs. The bounded scaling gate measures 1, 2, 4, 8, and 12 workers. A starts with 8 as the likely physical-core count and records Torch intra/inter-op thread settings. C normally reduces Torch CPU threads to 1 because inference and learning move to the GPU. Only the best stable measured setting becomes the default.

08 - Policy and action boundary

Batch rows by policy identity, not only by decision kind.

An A8 iteration uses the live shared policy and, on some iterations, one frozen snapshot or anchor seat. The manifest maps every seat to a policy_id and a record_for_ppo flag. The coordinator partitions ready rows by policy ID, evaluates each model in a batch, and returns actions for every seat. Only live-policy rows create trajectories.

Keyed categorical v1

The current Categorical.sample() consumes one shared Torch RNG stream, so changing batch order changes later actions. The native collector instead hashes immutable decision identity into a 32-bit uniform word. The policy computes the same masked categorical distribution and chooses the first cumulative probability crossing that word.

key = splitmix64(run_sampling_seed, policy_identity,
                 policy_version, game_id, seat_id, decision_sequence)
u = (low32(key) + 0.5) / 2**32
action = first_index(cumsum(masked_softmax(logits)) >= u)
logp = masked_log_softmax(logits)[action]
  • The hash is a named algorithm with unsigned overflow, not platform-dependent std::hash or Python hash().
  • Batch reorder, padding, worker count, and unrelated completed games must not change the action for a row.
  • CPU and GPU resume are each exact within their frozen runtime receipt; changing device mid-campaign remains forbidden.
  • This samples the intended categorical distribution but will not reproduce old scalar Torch RNG trajectories. That is why it is a new learned-policy recipe identity.

Batch dispatch

The boundary supports a row capacity and an optional maximum wait. Dispatch occurs when the buffer is full, no runnable game remains, or the oldest ready group reaches the wait limit. Fixed-shape padding is supported because it can stabilize CPU/GPU kernels, but its actual row count and wait are deferred until A exposes real batch histograms. No hard-coded synthetic batch earns adoption.

09 - Trajectories and rewards

Store compact rows natively and finalize once per PPO iteration.

The native arena is chunked so a long game cannot require a giant fixed reservation. Blocks come from a preallocated free list. Each game/seat owns an ordered chain; completion publishes a descriptor, not copied rows. Finalization walks descriptors in canonical game/seat order and performs bulk copies into one training batch.

Reward closure

  • Pending state stores previous position, lap, and spun-out flag because the current A8 reward reads only those fields between decisions.
  • Terminal placement and margin read the final native game state.
  • A truncated game emits value-only bootstrap rows. The coordinator batches V(s_next); native code folds gamma * V(s_next) into the last reward and still stores done=True, matching the current collector.
  • Reward mode, shaping weight, spin penalty, margin coefficient, gamma, and GAE lambda are frozen iteration configuration and included in the schema/recipe receipt.

GAE plan

A8 integration first finalizes rewards/dones/values and reuses the existing Python RolloutBuffer.compute_gae semantics as the oracle. Once the batch is exact, a tight native reverse pass may compute GAE per game/seat stream. It is adopted only if its float32 outputs match the reference exactly and preparation time materially falls. C may instead compute GAE on the GPU if that is faster; the storage contract does not depend on where it runs.

CPython compatibility details

  • Import/export the complete version-3 random.Random.getstate() form: 624 words, index, and Gaussian cache.
  • Implement the same 53-bit random(), variable-width getrandbits(k), rejection-based _randbelow(n), and reverse Fisher-Yates shuffle used by the frozen Python runtime.
  • Test empty, one-card, power-of-two, and non-power-of-two shuffle lengths because rejection consumption differs.
  • Record Python major/minor and RNG contract version. A later Python RNG change is a schema migration, never a silent rebuild.

Receipt modes

  • Off: production hot path; only aggregate counters and failures.
  • Hash: incremental semantic hashes at decision boundaries for bounded canaries and repeat tests.
  • Full: fixed numeric state/event/decision receipts that Python materializes for differential diagnosis.
11 - Failures, shutdown, and telemetry

A native crash must not look like a slow training run.

Workers never throw across a thread boundary. They catch expected failures, write one fixed ErrorRecord, mark the slot FAULTED, and request a pool-wide stop. The coordinator stops admission, wakes parked threads, joins them with a bounded timeout, and raises a Python NativeEngineError containing the receipt.

Typed failures

  • Schema or codec mismatch at pool creation.
  • Track/card/state capacity overflow.
  • Illegal, missing, duplicate, or stale action submission.
  • Impossible phase/program-counter combination or invariant failure.
  • Ready/trajectory arena exhaustion after backpressure should have prevented it.
  • Worker heartbeat timeout, coordinator timeout, or shutdown timeout.
  • CUDA copy, stream, event, out-of-memory, or device failure in option C.

Always-on low-cost telemetry

Record games, transitions, forced/real decisions, decision kinds, branch counts, reshuffles, stress draws, truncations, ready-batch histogram, rows by policy ID, worker busy/parked time, queue wait, inference wait, arena high-water marks, manifest overshoot, throughput, and repeat spread. C adds H2D/D2H bytes and time, GPU inference/update time, stream idle time, allocated/reserved memory, utilization, temperature, power, and throttle reasons where available.

13 - Option C: GPU inference pipeline

The confirmed RTX 4080 SUPER accelerates batches; native CPU workers keep owning rules.

A read-only receipt on 21 July confirmed an NVIDIA GeForce RTX 4080 SUPER with 16,376 MiB VRAM, driver 596.49, and compute capability 8.9. The current repo environment uses PyTorch 2.13.0+cpu, so the exact CUDA wheel/toolkit pairing remains an implementation-time compatibility choice. Installing it is not authorized by this design.

native workers ---> pinned host buffer 0 --H2D--> CUDA inference --D2H--> actions
       |            pinned host buffer 1 --H2D--> CUDA inference --D2H--> actions
       |            pinned host buffer 2 --H2D--> CUDA inference --D2H--> actions
       +---- continue runnable games while other games wait for results ----+

after collection barrier:
compact trajectory --bulk H2D--> GPU tensors --> PPO epochs --> new policy version

Environment and ownership

  • Create a separate CUDA development environment first; do not replace the proven CPU-only environment until the CUDA smoke and resume receipts pass.
  • The native extension remains CPU-only and PyTorch-independent. CUDA streams and tensors are owned by the Python policy coordinator.
  • The live policy and the one selected snapshot/anchor model reside on the GPU for the iteration. The snapshot pool remains checkpointed on CPU; only the selected model is copied once per iteration.
  • Use FP32 eager inference first with TF32 and mixed precision disabled. Faster numerical modes are separate learning-affecting experiments.

Reusable pinned buffers

Python allocates two buffers initially and supports a third if overlap data proves useful. Each buffer contains pinned CPU tensors for observation, dense mask or packed mask, logical metadata, sampling words, and action/logp/value outputs. Their NumPy views are bound once to the native pool. No batch pins memory or allocates a new tensor.

  1. C0 - environment receipt: freeze GPU/driver/PyTorch/CUDA/compiler versions; CUDA policy smoke; CPU environment remains untouched.
  2. C1 - real-batch inference gate: benchmark eager FP32 on batch sizes actually emitted by A, including small tails and two policy identities.
  3. C2 - pinned buffer contract: bind reusable host buffers, lease states, non-blocking transfers, events, and fault injection.
  4. C3 - overlapped collection: double-buffer CPU simulation, transfers, and inference; add bounded wait/backpressure and stream telemetry.
  5. C4 - GPU PPO baseline: move finalized tensors, policy, optimizer, and update to CUDA without changing minibatch size, epochs, or objective.

  7. C6 - operational gate: fresh-process resume, matched full-loop repeats, one-hour thermal soak, then an eight-hour rehearsal.

Continue only if GPU inference improves the full collection loop by at least 1.25x. Adopt A+C at 5,000+ trained tps with less than 5% spread; target 6,500/s for the one-billion route.
14 - GPU PPO update design

Preserve the learning recipe before optimizing launch overhead.

The current workload uses a small 104-input MLP, 516 action logits, minibatches of 256, and five epochs in A8. The GPU can make matrix work cheap enough that Python/kernel launch overhead dominates. C therefore separates device migration from update-graph optimization.

C4 baseline

  • Bulk-copy the finalized iteration once. Unpack legal-mask bits into one GPU boolean tensor or compare a packed-mask kernel only if transfer measurements justify it.
  • Keep FP32 parameters, Adam state, losses, advantage normalization, minibatch size, epoch count, clip range, gradient clipping, and torch.randperm ordering semantics.
  • Keep the optimizer on the resolved device for the whole campaign. Resume rejects a device change.
  • Synchronize only for bounded timing, error checks, iteration completion, checkpoint copying, and scalar logging. Avoid .item() inside the minibatch loop.
  • Accumulate diagnostic loss sums as device tensors and transfer them once after the update.

C5 measured optimizations

  • Compile one fixed-shape full-minibatch function that accepts index tensors; handle the final partial minibatch eagerly so no samples are dropped or reweighted.
  • Require the same losses and parameter deltas within a frozen numerical tolerance on a fixed batch before timing.
  • Use CUDA graphs only if compile still leaves launch gaps and static buffers can preserve exact data/order semantics.
  • Do not change minibatch size, accumulate gradients, enable AMP/BF16, or alter epochs as a substrate optimization. Each changes the learning recipe and needs a separately registered generation and learning comparison.

Fallback combinations

GPU inference and GPU learning are gated independently. If inference passes but the update is slower, a temporary GPU-inference/CPU-update mode may be measured, including the once-per-iteration weight copy. It is a diagnostic fallback, not the preferred 800M design. If neither neural component improves the full loop, C stops and A remains the production result.

15 - Resume, provenance, and policy identity

Keep checkpoints at completed PPO boundaries; do not serialize live threads.

The existing D0 contract already checkpoints after a completed update. A and C retain that boundary. When a checkpoint is written, every admitted game has completed, every trajectory row has been consumed, the pool is drained, and there is no in-flight native state. A hard failure loses at most the current iteration and resumes from the previous verified checkpoint.

New training-state fields

  • Collector kind and native protocol/state/codec/RNG/receipt versions.
  • Native source identity, compiler/build receipt, and production/debug mode.
  • Worker count, queue/buffer capacities, chosen dispatch policy, Torch thread counts.
  • Next logical game ID, sampling seed/version, rows-per-game estimator state, and manifest formula version.
  • Resolved device plus, for C, GPU model, driver, PyTorch CUDA build, precision flags, stream/buffer configuration, and compiled-update identity.
  • Existing live policy, optimizer, controller, snapshot pool, seat schedule, NumPy/Torch RNG, progress, campaign, source, recipe, and anchor identity.

Stop behaviour

  • A normal stop stops new iteration admission, finishes the current iteration, performs its update, saves atomically, and exits.
  • A requested bounded test stop may drain admitted games and discard the uncommitted iteration only in a smoke tool, never in a registered training campaign.
  • A native or CUDA fault aborts the current iteration without updating. The last completed checkpoint remains authoritative.
  • Fresh-process resume must reproduce the uninterrupted training-state digest for the same runtime and configuration.
Generation rule. Native collection and keyed categorical sampling can change learned weights even when the probability distribution and game semantics are correct. The first non-smoke A campaign therefore allocates the next immutable G#### identity after its resolved recipe and source are frozen. A later CUDA/precision/update-recipe change also receives a new generation when it can affect weights.
