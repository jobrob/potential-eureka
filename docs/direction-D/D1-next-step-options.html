Option B selected - 20 July 2026

Two sensible ways forward after D1.

D1 proved that we can batch policy decisions correctly. It missed its speed gate because the Python game engine still performed too much extra work. The next solution should either run several exact engines at the same time, or make the engine itself much faster.

Direction D - design choices
Evidence: D1 implementation and benchmark

Current state Scalar stays trusted.

Do not tune the rejected lane counts again. Choose one new idea, give it a small gate, and stop if it does not earn the next step.

01 - What must change

Batching worked. Extra game work was the problem.

At 16 lanes, policy inference fell from about 41 seconds to 6.5 seconds. But closing unfinished seat actions added about 49,000 extra game actions for every 99,000 actions kept for training. We saved inference time, then spent much of it moving the games to safe stopping points.

02 - Option A

Several CPU workers, one shared learner.

Simple idea: keep the current exact game engine. Freeze one copy of the policy, send it to three worker processes, and let each worker play complete games. Bring all their trajectories back and perform one PPO update in the main process.

one frozen policy
       |
       +-- worker 1 plays complete games --+
       +-- worker 2 plays complete games --+--> one PPO update
       +-- worker 3 plays complete games --+

Why it may work

  • Complete games avoid D1's bridge-action drain.
  • Terminal rewards remain common and easy to understand.
  • The rules engine is unchanged, so semantic risk is low.
  • The project already measured about 2.7x throughput from three independent workers. This is not the same design, but it shows the machine can use three workers well.
  • Training checkpoints remain simple because workers finish before the PPO update and only central training state is saved.

Main risks

  • Moving trajectories and policy weights between Windows processes has a cost.
  • Worker seeds and result ordering must be exact for segmented resume.
  • Each worker still performs scalar policy inference, so the final gain may be smaller than the earlier independent-worker result.
  • This may be a good CPU solution without reaching Direction D's full long-term target.
Small gate: build a three-worker synchronous prototype using the current engine and one frozen policy version. Compare one and three workers on three matched 20k-transition development runs. Continue at 1.5x or better; stop below 1.3x. Estimated code: 500-900 lines. Estimated compute: under 30 minutes.
03 - Option B

Build one exact tensor-engine slice.

Simple idea: keep the D1 collector and its policy batches, but replace one slow part of the Python rules engine with batched PyTorch state and rule operations. Start with one complete phase-to-phase slice, not the whole game.

many game states as tensors
            |
      one exact phase kernel
            |
   batched observations and decisions
            |
        existing D1 collector

Why it may work

  • D1 proved that large policy batches are available.
  • The remaining measured cost is mostly game simulation, which this option directly attacks.
  • Tensor state makes the current extra drain actions much cheaper.
  • An explicit phase state is easier to save and resume than a hidden Python generator.
  • This is the clearest route toward larger CPU batches and, later, CUDA.

Main risks

  • It is a much larger rules rewrite.
  • Every rule must match the legacy engine exactly.
  • A fast small kernel may still fail to improve the complete training loop.
  • The first slice may reveal that Heat's branch-heavy rules do not map cleanly to tensors.
Small gate: implement one representative exact phase slice with fixed-shape state and differential tests against the legacy engine. Continue only with zero semantic differences, at least 3x kernel speed, and a D1-based projection of at least 1.5x end-to-end. Target 5x kernel speed. Estimated code: 1,200-2,000 lines. Estimated compute: under one hour after correctness passes.

05 - Recommendation

Option B has been selected.

The project will pursue the more ambitious tensor-engine route. The detailed D2 design splits it into six gated chunks, starting with tensor state and ending with a bounded kernel benchmark.

Option A remains a fallback if the tensor representation cannot preserve exact rules or cannot reach its kernel speed gate.

Not recommended now: more 8/16/32-lane tuning, more phase-only batching, or a full tensor-engine rewrite in one step. D1 already answered the first two, and the last is too large without a vertical-slice gate.
