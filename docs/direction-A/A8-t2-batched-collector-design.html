01 · Design decision

Make the first batch inside each game, not across 32 games.

The rules engine already treats GEAR and CARDS as simultaneous: it collects every active player’s choice before applying any choice. The collector currently sends those choices through the policy one at a time. T2 should gather the same observations and masks, call policy.act once, then replay the sampled actions through the unchanged driver.

ResultThe reversible first slice was implemented and measured. Keep scalar as the A8 and CLI default. Retain opt-in phase as a tested diagnostic path, but do not implement adaptive lanes: median rollout gain was only 1.066× and live inference wall fell 13.55%.

02 · Why the design changed

P0 supports batching, but not a large game pool yet.

P0 found that rollout consumed 75.7% of measured training time and live-policy inference alone consumed 44.9%. That establishes the target. The same log shows why the earlier 16–32-game sketch is unsafe at the current update size:

A8 averages only 4.24 completed games per PPO iteration. Starting 16 six-seat games would collect roughly 9,800 transitions before all in-flight games finish—almost ten times the configured rollout. That would change PPO update frequency and temporal correlation at the same time as the performance code.

Design feedback. The original vectorized-collector idea is more complicated than it first appeared because A8 stores rewards over the span from one seat decision to its next decision and computes GAE on complete per-seat streams. Cutting arbitrary lanes at 1,024 transitions would require a new partial-trajectory and bootstrap contract. T2 should not take that on before proving smaller batches are worthwhile.

Shared enumeration, not duplicated rules

Extract small helpers in engine/driver.py that return the GEAR or CARDS Decision objects in the exact order the driver uses. The driver itself and the batched collector both call these helpers. This prevents legality, spun-out handling, active-player filtering, and seat order from drifting.

There is one prerequisite cleanup: the driver currently sets player.cluttered immediately after each card choice, although phase_play_cards already performs the same detection when all choices are applied. Remove that duplicate early write and retain the phase-level write. This makes simultaneous decision collection genuinely read-only and prevents later agents from observing a transient flag from an earlier seat.

def simultaneous_decisions(state, kind) -> list[Decision]:
    """Return the unapplied choices for one simultaneous phase."""

if batching and decision.kind in {GEAR, CARDS}:
    ready = prepare_phase(simultaneous_decisions(state, decision.kind))
    actions, logps, values, _ = policy.act(stack_obs(ready), stack_masks(ready))
    queue_phase_actions(ready, actions, logps, values)

send_value = queued_action(decision.kind, decision.player_id)

Snapshot opponent handling

The A5 recipe uses one frozen snapshot seat in roughly half of iterations. In the first slice, resolve that seat through its existing SnapshotAgent in the same active-player order and batch only live-policy seats. This preserves the recipe and keeps the change small. Telemetry must count snapshot inference separately; if it becomes the dominant residual, a later local extension may batch the one frozen model too.

Why the scalar path remains

Add a collector mode such as collector_mode="scalar" | "phase", defaulting to scalar until T2 passes. The current branch remains available as a reference implementation, a debugging escape hatch, and the exact evaluator path. Do not delete or silently replace it during the spike.

05 · Correctness and determinism

Preserve semantics; acknowledge the one intentional difference.

  • Whole-game collection remains unchanged. Every non-empty stream still ends on done=True; GAE continues to use a zero bootstrap.
  • One buffer per seat remains unchanged. No concurrent games exist in the first slice, so streams cannot interleave.
  • Rewards close at the same state. After the duplicate pre-application cluttered write is removed, GEAR and CARDS do not mutate state until all decisions are collected. Closing every seat’s pending span before the batch then matches the scalar collector.
  • Legality is shared. The same forced_action, legal_action_mask, and decode_legal_action functions remain authoritative.
  • Fixed order is mandatory. Stack live choices in the driver’s active-player order and scatter results back in that same order.
  • Repeated phase-mode runs must match exactly. Given the same configuration, Torch seed, and game seed, action traces and buffers must hash identically.
Expected stochastic difference. PyTorch’s categorical sampler consumes randomness differently for a batch than for repeated batch-of-one calls. A sampled phase-mode trace is therefore not expected to equal the old scalar trace even with the same Torch seed. Correctness equivalence must use a deterministic fixture policy; stochastic testing checks repeatability and distributional legality, not byte identity with scalar sampling.

07 · Focused verification

Test the new seam, not every old rule again.

  1. Decision-helper identity and purity. On seeded 2- and 6-seat states, helper decisions match the driver’s yielded GEAR/CARDS kinds, seats, and legal payloads; collecting all choices leaves the pre-application state unchanged.
  2. Deterministic trace equivalence. A fixture policy chooses a deterministic legal action per row. Scalar and phase modes must produce identical action traces, terminal states, rewards, dones, and per-seat buffers.
  3. Stochastic reproducibility. Two independent phase-mode runs with equal seeds produce equal action/buffer hashes; a changed seed changes at least one action.
  4. Batch accounting. Every real live-policy decision appears in exactly one inference call; forced and snapshot decisions do not enter the live batch.
  5. Existing focused suite. Re-run multi-seat, A5 snapshot, and A8 tests. No broad new rule matrix is needed because the driver remains authoritative.

09 · Measured result

Correct batching was real, but the batches were too small.

The correctness gate passed before performance work: a deterministic fixture produced identical scalar and phase action traces, terminal states, rewards, dones, and per-seat buffers; repeated stochastic phase runs matched exactly at equal seeds; changed seeds changed actions; stored actions were legal; every non-empty stream ended on done=True; and live decisions reconciled exactly to inference rows and the batch histogram. The focused multi-seat and A8 suites reported 21 passing tests, and Ruff passed on all touched Python files.

All phase seeds avoided the “more than 5% slower” guard, but that secondary safety gate cannot override the primary thresholds. Across phase repeats, 380,264 live decisions used 282,517 action calls: 25.7% fewer calls per live row, yet the actual mean call batch was only 1.346. Roughly half of decisions remain sequential, so the 2.0–2.1 available simultaneous batch could not produce the predicted end-to-end gain.

VerdictReject phase mode as the production default and stop T2 after T2b. Preserve the scalar reference and opt-in phase implementation for debugging or future collector research. T2c adaptive lanes, T2d CUDA, and the separate 300k learning-safety experiment were not started.
