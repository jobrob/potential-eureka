Q01 · Question and evidence role

Two questions. Only one of them is a runtime-adoption gate.

Choose before registration
Question A asks whether the native 32K collector preserves G0002-level learning when the observation is still codec v3. Question B asks whether codec v4, with absolute corner scales and the missing react context, learns better. Question B changes the inputs and the runtime together. It must not be reported as “the same policy, faster.” G0005 stays unallocated until one question is written down as its own recipe.
Question ADoes the native 32K runtime, with the legacy codec v3 observation, preserve G0002-level learning at the 1M scale well enough to be a substrate for later work?
Question BDoes a new recipe that trains on codec v4 beat the preserved G0002 baseline on the same races? Report it as an input change plus a runtime change.
Hypothesis for AThe candidate passes the aggregate, matched-run, breadth, and collapse guards. Those guards are an engineering tolerance for a three-seed pilot, not a precise non-inferiority claim.
Prior confidenceMedium, 60%, for question A. The one-hour soak is strong. Thirty updates, a coarser opponent refresh, and seed instability remain real risks. Question B has no learning evidence yet.
Positive result meansFor A: later work may keep this runtime and the legacy observation. For B: later work may keep the corrected observation. Neither result means the car is near a skilled human.
Positive result does not meanThe candidate is the final training method, or that equal transition counts made the two schedules the same.

Five epochs over batch-256 minibatches keep roughly the same number of times each collected row is reused. That is not the same learning schedule as G0002. G0002 took a PPO step about every 1,024 rows, so a 1M run had on the order of a thousand updates and many updates at each seat count. Thirty updates of 32,768 rows is about six updates per seat count. Snapshot spacing, how long an opponent copy stays in the pool, and how fast the entropy controller can react all change. Say that in the report. Do not fold optimizer, reward, anchor, curriculum, track-distribution, precision, CUDA, or model-size tuning into the same comparison.

The trainer now logs rollout_entropy separately from update_entropy, plus approximate KL, clip fraction, and value explained variance. Those are measurements. They are not a new early-stop rule. The collapse guard reads rollout_entropy, which is the value the controller saw, not the entropy averaged inside the optimizer.

Q03 · Training and checkpoints

Stop on actual transitions, with a hard cap.

  1. Fresh
    seeded policy initialization
  2. Large updates
    32,768 requested rows each
  3. First crossing
    300K, 500K, 750K, and 1M actual rows
  4. 1M selected
    the first update that crosses 1M
ContractFrozen behavior
Stopping ruleThirty requested updates of 32,768 rows are 983,040 rows. That does not guarantee 1,000,000 actual transitions. Stop at the first completed update whose actual row count is at least 1,000,000. Also stop at 40 updates or at the per-run time cap, whichever comes first. A run that hits a cap before 1M is an operational fault, not a selected checkpoint.
Actual rowsNative collection drains admitted games, so a completed update can record more rows than it requested. Every checkpoint stores the threshold it was asked to cross and the exact actual count.
MilestonesThe first completed update that crosses 300K, 500K, 750K, and 1M actual recorded transitions. Diagnostic scores cannot replace the 1M checkpoint after the scores are known.
SelectionThe 1M first-crossing checkpoint represents every run in promotion. Earlier scores cannot replace it.
SnapshotsOne policy snapshot after each update. Only the latest five stay in the rolling opponent pool.
RecoveryFull-state save every five updates and at completion. The save publishes a latest pointer only after the checkpoint and its receipt both exist, and it keeps the previous pair. A failed save must leave the last good pair loadable. The normal gap is still five completed updates.

The resumable state includes policy, optimizer, entropy controller, snapshot pool, schedule, private RNGs, Torch RNG, native collector state, recipe and source identities, counters, emitted milestones, and diagnostic rows. A disposable two-update fresh-process smoke must prove that snapshot use and complete-state resume remain valid before registration.

Q06 · Small predeclared gate set

Every adoption guard must pass.

For each run, compute an equal-weight mean across the 12 ruler × seat promotion cells. Recipe scores are medians across the three runs. Ruler and seat slices first average equally within each run and then take the three-run median.

Q08 · Required response to FAIL

A failed gate starts analysis, not automatic retuning.

An evidence-valid FAIL automatically authorizes a bounded offline investigation using the completed artifacts. Reproduce the failed gate from raw rows; localize it by seed, milestone, ruler, seat, track, and start; inspect entropy/controller history, PPO losses, opponent sources, snapshots, actual rows, and overshoot; then rank plausible causes.

Failure patternFirst investigation branch
All seeds and rulers weak from early milestonesUpdate cadence, initialization-to-first-update behavior, advantage/update accounting, and opponent availability.
One coherent seed regressionTraining-seed sensitivity, checkpoint path, opponent-source sequence, and trajectory divergence.
Late regression after earlier strengthCheckpoint oscillation, entropy/controller response, self-play forgetting, and snapshot composition.
One ruler or seat slice weakDecision/loss replay on the failing style, traffic regime, and starting-position concentration.
Collapse guard failsEntropy and action-distribution timeline, controller saturation, value/policy loss, and skill consequence.

The investigation produces a human-readable HTML report and a local needs-triage issue. It does not authorize more races, training, hyperparameter changes, a new generation, CUDA, or scale beyond 1M.
